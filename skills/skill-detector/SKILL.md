# SKILL 检测 — 全方位 Skill 质量检测系统

基于 `sunxingboo/skill-evaluator`（MIT，多模型打分框架）整合改编，并参考 `lanyasheng/skill-evaluator`（无许可证，仅取红队测试与自主改进循环的方法思路）。**本 Skill 不是纯自研**：其中 4 个文件逐行来自 MIT 上游，原 LICENSE 已原样保留在本目录。完整来源、许可证状态与逐行比对结论见本目录 `ATTRIBUTION.md` 与仓根 `ATTRIBUTION.md`。

## 这个 Skill 解决什么

把「这个 Skill 到底好不好、能不能发布、两个 Skill 怎么横比」从主观印象拆成可复核的检查项：结构检查定能力等级，8 维加权打分定质量分，红队测试定安全边界，多模型交叉验证收敛分歧，自主改进循环在守住评估口径的前提下小步迭代。

不做的事：不替你写 Skill（用 `skill-writer`），不判断某条经验值不值得沉淀（用 `self-evolution`）。

## 使用场景

| 场景 | 说明 |
|------|------|
| 新 Skill 评审 | 开发完成后全面质量评估 |
| Skill 对比 | 两个及以上 Skill 横向对比排行 |
| 安全检查 | 红队测试：注入攻击、路径遍历、资源限制等 |
| 持续改进 | Karpathy Loop 自主迭代优化 |
| 发布前审计 | 达到 Level 2/3 标准发布 |

## 什么时候不用

- 被评对象还没有 `SKILL.md`（连 frontmatter 都没有）→ 先补结构，再评
- 用户只想改一处措辞或排版 → 直接改，不必开一次完整评估
- 用户要的是"该不该保留这条经验"的决策 → `self-evolution`
- 用户要求在真实生产环境里跑攻击载荷 → 拒绝；红队只在隔离、只读环境执行

## 输入：评估前先确认

1. **评估对象**：`skills/<name>/` 目录或单份 `SKILL.md` 文本。读不到就问用户要路径，不要凭目录名猜内容。
2. **模式**：默认快速模式。用户没明说「深度 / 全面 / 多模型」时不要自行升级——深度模式要跑 5-10 轮。
3. **是否允许改文件**：只有改进模式会改文件，且必须先备份；快速 / 深度 / 对比模式全程只读。
4. **是否允许外部调用**：策略 B（千帆 API）需要 Token，默认不跑，由用户显式提供。

## 检测流程

```
加载 Skill → 结构检查 → 8维打分 → [红队测试] → [多模型验证] → 综合报告 → [自主改进]
```

### 快速模式 vs 深度模式

| 模式 | 触发词 | 内容 | 耗时 |
|------|--------|------|------|
| **快速**（默认） | 检测/评审/打分 | 结构检查 + 8维打分 + 改进建议 | ~1-2轮 |
| **深度** | 深度检测/全面审计/多模型 | 快速 + 红队测试 + 多模型交叉验证 | ~5-10轮 |
| **对比** | 对比/比较/排行 | 多个 Skill 快速模式 + 并列分析 | ~N轮 |
| **改进** | 改进/优化/提升 | 深度 + Karpathy Loop 自主迭代 | ~10+轮 |

## 阶段 1：结构检查

检查目标 Skill 的基础完整性：

| 检查项 | Level 1 | Level 2 | Level 3 |
|--------|---------|---------|---------|
| SKILL.md 存在 | ✅ 必须 | ✅ 必须 | ✅ 必须 |
| frontmatter (name/description) | ✅ 必须 | ✅ 必须 | ✅ 必须 |
| scripts/ 目录 | 可选 | ✅ 必须 | ✅ 必须 |
| references/ 目录 | 可选 | 可选 | ✅ 必须 |
| tests/ 目录 | ❌ | ❌ | ✅ 必须 |
| README.md | 可选 | ✅ 必须 | ✅ 必须 |
| 错误处理 | 基本 | 完整 | 完整+降级 |
| 测试覆盖率 | — | >80% | >95% |

**等级判定**：

- **Level 1**：有 SKILL.md + name + description → 基础可用
- **Level 2**：Level 1 + scripts/ + 错误处理 + README + 测试>80% → 稳定可靠
- **Level 3**：Level 2 + references/ + tests/ + 测试>95% + 反馈循环 → 生产就绪

## 阶段 2：8 维度打分

评分标准唯一来源是 `references/dimensions.md`。各维度独立评分（0-10），加权计算总分。

| 维度 | 权重 | 核心评估点 |
|------|------|-----------|
| D1. 元数据质量 | 15% | name/description 是否精确，含触发/排除条件 |
| D2. 执行引导清晰度 | 15% | Agent 加载后能否正确决策，分支逻辑是否完备 |
| D3. 领域知识密度 | 15% | 是否内嵌了通用 Agent 不具备的专业知识 |
| D4. 工作流完整性 | 15% | 端到端工作流是否清晰，含异常处理 |
| D5. 输入输出清晰度 | 10% | 用户是否知道该提供什么、能得到什么 |
| D6. 资源利用 | 10% | scripts/references/assets 利用是否合理 |
| D7. 写作质量 | 10% | 结构清晰、可扫读、无冗余 |
| D8. 范围与聚焦 | 10% | 是否专注单一问题域，不过宽不过窄 |

**综合得分 = D1×0.15 + D2×0.15 + D3×0.15 + D4×0.15 + D5×0.10 + D6×0.10 + D7×0.10 + D8×0.10**

| 分数 | 等级 | 含义 |
|------|------|------|
| 9.0-10 | S | 标杆级 |
| 7.5-8.9 | A | 优秀，可发布 |
| 6.0-7.4 | B | 合格，有明显改进空间 |
| 4.0-5.9 | C | 较弱，需大幅修改 |
| 0-3.9 | D | 存在根本性问题 |

打分时每一维都引用被评 `SKILL.md` 里的原文片段作为证据；没有证据可引的维度记"信息不足"并说明，不要给一个看起来合理的分数。

## 阶段 3：红队测试（深度模式）

对 Skill 进行 5 类安全攻击测试，用例与判定标准见 `references/red-team.md`。

| 测试类型 | 用例数 | 说明 |
|----------|--------|------|
| SQL 注入 | 4 | '; DROP TABLE / OR '1'='1 等 |
| 提示词注入 | 4 | 忽略指令 / 角色越狱 / 系统指令覆盖 |
| 资源限制 | 3 | 大输入 100KB/1MB / 嵌套 JSON |
| XSS 攻击 | 4 | script/img/iframe/javascript: 注入 |
| 路径遍历 | 4 | ../../../etc/passwd / C:\Windows\System32 等 |

**通过标准**：所有攻击被安全处理（拒绝/转义/限流），通过率 ≥ 90%。

执行约束：载荷只读不执行——不真的连数据库、不真的读系统文件、不发起网络请求；全部在隔离环境里做静态判定。

## 阶段 4：多模型交叉验证（深度模式）

提示词见 `references/prompts.md`。三种策略自动降级：

| 策略 | 说明 | 依赖 |
|------|------|------|
| A: 并行多模型 | 多个真实模型并行独立评估+交叉互审+仲裁 | Agent 工具 + model 参数 |
| B: 千帆 API | 通过百度千帆 API 调用多模型 | `scripts/qianfan_chat.py` + Token |
| C: 串行多视角 | 同模型依次扮演严格/务实/专家三视角 | 无外部依赖 |

**默认模型**（用户未指定时）：

- 主模型（仲裁者）：当前 Agent 自身
- 评估模型：sonnet, glm-5, minimax-m2

**千帆 API 配置**：Token 读取优先级 `config.json → $QIANFAN_BEARER_TOKEN → 询问用户`，详见 `scripts/qianfan_chat.py`。

模型确认交互最多 2 轮（模型选择 + Token），多数情况一键默认即可开始。模型间分歧保留原样并写出仲裁理由，不要用平均分掩盖分歧。

## 阶段 5：自主改进循环（改进模式）

Karpathy Loop 流程（参数与决策规则见 `references/self-improve.md`）：

```
提出小改动 → 运行评估 → 保留(得分提升)/回滚(得分不变或下降) → 重复
```

- 改动类型：优化 prompt 措辞 / 改进错误处理 / 添加边界检查 / 优化资源限制
- 最多迭代 100 次，连续 10 次无改进则早期停止
- 每次迭代前自动备份，确保可回滚
- 开跑前先固定评估口径（同一套维度定义、同一份证据标准），否则每轮都会"感觉变好了"

## 输出与验收

报告模板见 `references/report-formats.md`（单模型 / 多模型 / 单模型多视角三种）。

一份报告算完成，需要同时满足：

- 8 个维度都有分数，没有"未评"
- 每个扣分点都能指到被评 `SKILL.md` 的具体段落或原文
- 问题与建议一一对应（一条问题跟一条可执行建议）
- 结论（总分、等级、Level）与分数表不矛盾
- 深度模式给出共识度标注（一致 / 多数 / 仲裁），对比模式给出并列评分表与排名理由
- 改进模式给出迭代次数、保留 / 回滚记录与最终得分

## Gotchas

1. **只给总分不给证据** → 报告不可复核，改进也无从下手。每个维度引用一句原文。
2. **把启发式分数当客观测量** → 换模型、换轮次波动 1-2 分是正常的，不要当 SLA 或排名依据。
3. **没有固定口径就开改进循环** → 每轮都"感觉变好了"。先冻结维度定义与证据标准，再迭代。
4. **在真实环境跑红队载荷** → 越权、破坏、留痕。只在隔离环境、只读执行。
5. **快速模式越界成深度模式** → 用户只想 30 秒看一眼，却等了 10 轮。默认快速，升级要用户点头。
6. **评估对象靠目录名猜内容** → 评出来的是一份想象中的 Skill。先 `read` 到真实文本再打分。

## 边界与免责

- 打分是**启发式评估**，不是客观测量；不同模型、不同轮次的结果会有波动，不应当作 SLA 或排名依据。
- 红队用例是通用安全载荷，不构成完整安全审计；涉及生产环境请另做专业测试。
- 自主改进循环有迭代上限与早停条件，且每轮自动备份，仍建议只在工作副本上跑。
- 本 Skill 不改写被评对象；改进是"提出候选改动 + 让用户确认"，不是静默替换。

## 与本仓其他 Skill 的交接

| 结论 | 下一步 |
|---|---|
| 结构缺失、触发词含糊、要重写 | `skill-writer` |
| 分数够但用过之后要决定改 / 留 / 忘 | `self-evolution` |
| 只想快速找短板 | 留在本 Skill 快速模式 |
| 要连续小步优化且能接受多轮评估 | 本 Skill 改进模式 |
