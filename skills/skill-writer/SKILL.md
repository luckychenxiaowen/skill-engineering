# skill-writer — 把素材写成一份可加载的 Skill

## 这个 Skill 解决什么

有一段素材，不等于有一个 Skill。素材是「知道」，Skill 是「Agent 在特定场景下能照着做」。本 Skill 负责这段转换：定问题域 → 拆结构 → 起草 → 自查 → 按渐进式披露交付。

不做的事：不润色普通文章，不给已有 Skill 打分，不决定某个 Skill 该不该保留。

## 什么时候用

- 有一篇方法论文章 / 一套踩坑笔记 / 一段对话里反复出现的做法，想固化成可复用 Skill
- 已有 `SKILL.md` 但触发词含糊：Agent 经常不加载，或在无关场景误加载
- 一批素材要产出多个 Skill，且要求术语、格式、目录结构一致
- 要给现有 Skill 补 frontmatter、补输入输出契约、补边界

## 什么时候不用

- 用户只是让你改写或润色一段普通文本 → 普通写作任务，本 Skill 不适用
- 用户问「这个 Skill 好不好、打几分」→ 用 `skill-detector`
- 用户问「这个 Skill 用过之后该改还是该删」→ 用 `self-evolution`
- 用户只给了一句愿望（"帮我写个 skill"），既没有素材也不说场景 → 先追问，不要凭空造

## 输入：动手前必须确认的三件事

1. **谁、在什么场景用**：用户原话里的触发场景（"每次发版前"、"客户问报价时"）
2. **成功长什么样**：可观察的结果（一份报告 / 一个改动 / 一次判断）
3. **素材边界**：哪些是事实与数据（必须保留），哪些是观点（可改写），是否含不能进仓的内容（凭据、真实 AppID、雇主语境）

缺第 1、2 项 → 追问一轮（最多 3 个问题），不要边猜边写。追问不到就写「由使用者判断」，不要编阈值。

## 产出契约

一个 Skill = 一个目录：

```text
skills/<name>/
  SKILL.md      # 必需：frontmatter + 执行引导
  README.md     # 必需：解决什么问题 / 怎么用 / 依赖 / 与谁配合
  references/   # 可选：长模板、长表格、领域细节
  scripts/      # 可选：确定性、可重复的操作
```

交付时逐项说明：产出了哪些文件、每个文件为什么存在、哪些内容被推迟到 `references/`。

## 五步流程

### 第 1 步：定问题域

用一句话写清「谁、在什么场景、要什么结果」，再写一句「不解决什么」。
问题域过宽（"帮人写东西"）或过窄（"改一个按钮文案"）都要收敛或放弃。

### 第 2 步：把素材拆成四类内容

| 类别 | 从素材里找什么 | 写成什么 |
|---|---|---|
| 触发 | 用户会怎么说、什么信号出现时该用 | description 里的正向触发词 |
| 步骤 | 做过一次以上的固定动作、有顺序依赖 | 编号流程，每步有输入和输出 |
| 判据 | "这样就算对了"的可检查条件 | 验收清单 / 阈值 / 反例 |
| 反例 | 踩过的坑、看起来对但错的做法 | Gotchas 一节 |

四类里缺哪类，就去素材里补；素材里确实没有判据的，在 Skill 里明说"由使用者判断"。

### 第 3 步：起草 SKILL.md

结构固定为：frontmatter → 这个 Skill 解决什么 → 什么时候用 / 不用 → 输入 → 流程 → 判据 → 输出 → Gotchas → 边界。

```markdown
---
name: <小写连字符，与目录名一致>
description: >
  <做什么>。当用户说「A」「B」「C」时使用。
  TRIGGER when: <正向场景>
  DO NOT TRIGGER when: <相邻但不同的事>
version: 1.0.0
---

# <name> — <一句话定位>

## 这个 Skill 解决什么
## 什么时候用 / 什么时候不用
## 输入（动手前确认什么）
## 流程（编号步骤，每步有输入输出）
## 判据（怎么算做完）
## 输出（交付什么、什么格式）
## Gotchas（最容易错的三到五条）
## 边界（不做什么、依赖什么）
```

写法要求：

- 祈使句、短句、具体动词；一个步骤一件事
- 每条规则尽量带一个反例或阈值
- 不写「合理」「高质量」「适当」这类没有判据的词

### 第 4 步：触发词与 frontmatter 自查

- `name`：小写字母、数字、连字符；与目录名一致；不用中文、空格、下划线
- `description`：第一句说做什么，之后写触发；同时写正向触发与反向排除；控制在 200 字以内
- 触发词用**用户的真实说法**（口语 + 同义写法），不用内部术语或文件名词
- 与相邻 Skill 容易混淆时，在 description 里点名排除（"DO NOT TRIGGER when ..."）
- 触发词宁窄勿宽：误加载比不加载更贵

### 第 5 步：渐进式披露与交付

- `SKILL.md` 只放每次执行都要用的内容；超过一屏的长表格、长模板、大段示例移到 `references/`
- 确定性、可重复的计算或转换写成 `scripts/`，SKILL.md 里只写"什么时候调用、参数是什么"
- 每个 `references/` 文件在 SKILL.md 里有一句"什么时候读它"
- 同步 `README.md`（解决什么问题 / 怎么用 / 依赖与凭据 / 与谁配合）与 `CHANGELOG.md`
- 跑仓库的提交前检查（如 `python scripts/check-before-push.py`），全项通过再交付

## 输出格式

```text
【产出】
- skills/<name>/SKILL.md（N 行）
- skills/<name>/README.md
- references/...（如有）

【问题域】谁 / 什么场景 / 什么结果
【触发】正向：...；排除：...
【判据】...
【待确认】...（没有就写"无"）
【建议下一步】用 skill-detector 快速模式打分
```

## Gotchas

1. **把文章改写成 Skill**：只做了摘要和分段，没有触发词、没有判据，Agent 加载后仍不知道何时用。**做法**：先拆四类内容（触发 / 步骤 / 判据 / 反例），再动笔。
2. **触发词写成文件名**："用 skill-writer" 不是触发条件，"把这个经验写成 skill" 才是。**做法**：用用户的说法，不用内部命名。
3. **description 写成一整段背景介绍**：加载器拿它做匹配，背景越长越容易误触发。**做法**：做什么 + 何时用 + 何时不用，200 字内。
4. **所有细节塞进 SKILL.md**：文件越写越长，每次加载都付上下文成本。**做法**：能推迟读的放 `references/`。
5. **编造阈值**：素材里没有的百分比、次数、耗时不要写死。**做法**：留空并标注"由使用者设定"。
6. **整段搬运第三方文本**：只蒸馏方法；确需引入代码或文本时登记来源与许可证，并在目录内保留上游 LICENSE。

## 边界

- 产出的是文档级 Skill，不是运行时框架；不负责执行环境、部署与权限
- 不替使用者决定某个 Skill 该不该存在，只负责把它写清楚
- 不接收凭据、真实 AppID、雇主内部语境作为素材
- 素材不足以支撑判据时，明确写出"待确认"，不补想象

## 交给下游

| 下一步 | 用什么 | 得到什么 |
|---|---|---|
| 发布前打分 | `skill-detector` 快速模式 | 8 维得分 + 改进建议 |
| 真实用一次 | 实际任务 | 触发与效果记录 |
| 决定改 / 留 / 忘 | `self-evolution` | 复盘结论与沉淀决策 |

（`skill-detector` / `self-evolution` 是本仓的生命周期配套 Skill；单独复制本 Skill 也能用，此时跳过下游两步。）
